# Стратегия тестирования

## 1. Принципы

- Юнит-тесты запускаются через `uv run pytest` **без Docker** — только чистый Python-код с фейками (in-memory SQLite не используем: полагаться на общую SQL-логику не будем, фейковые репозитории/сервисы вместо БД).
- Интеграционные тесты требуют PostgreSQL/Silo/Redis — помечены маркером `@pytest.mark.integration`, запускаются только после вашего подтверждения (см. рабочие правила).
- Порядок работы: тесты → код (red-green). Для задач, где тест не имеет смысла (шаблоны, конфиги NGINX), — ручная проверка с чек-листом. Исключение — конфиг NGINX: `tests/test_nginx_template_render.py` рендерит `nginx/default.conf.template` так же, как контейнер (envsubst с фильтром `NGINX_ENVSUBST_FILTER=^CSP_`), и требует: нет нераскрытых `${...}`, неизвестных nginx-переменных и имени в комментарии отсутствующего в конфиге (например `csp_media_origin` после комментария `$variable`), `$host`/`$remote_addr`/`$scheme`/`$http_range` на месте, в CSP реальный адрес хранилища, в compose нет монтирования в `/etc/nginx/conf.d/` и есть монтирование в `/etc/nginx/templates/` (ADR-008). `nginx -t` по отрендеренному конфигу — под маркером `integration`, если бинарник есть в системе.
  - Тест содержит `_strip_comment_lines`: конструкции вида `$host` в тексте комментария nginx не обрабатывает, поэтому проверка имён переменных идёт только по директивам.
- Ручные проверки: формат «команда → ожидаемый результат → что прислать обратно».

## 2. Обязательные покрытия (по ТЗ)

| Область | Что именно проверяем | Тип тестов |
|---|---|---|
| Приватность | Приватное видео: владелец видит, пользователь из белого списка видит, посторонний и гость получают 404; прямой presigned-URL приватного видео не выдаётся без прав; бакет raw недоступен | unit (логика check_video_access с фейками) + integration (эндпоинты) |
| Роли | user не открывает /moderation; moderator открывает и может скрыть видео; admin может менять роли; заблокированный (is_blocked) не проходит никуда, кроме логина | unit + integration |
| Загрузка | Отказ без сессии; отказ на расширение вне whitelist; отказ на неверные magic bytes; отказ при превышении MAX_UPLOAD_SIZE; успех создаёт videos.status=processing и ставит задачу | unit (валидаторы с фейковым стримом) + integration |
| Модерация | Жалоба создаёт reports.status=new; модератор скрывает видео → статус hidden → из ленты исчезает, прямой URL /videos/{id} → 404 для всех, кроме владельца/модератора; dismiss закрывает | unit + integration |
| Просмотры | Повторный просмотр за 24 ч не инкрементирует view_count; после 24 ч — инкрементирует; гость дедуплицируется по cookie-фингерпринту | unit |
| Сессии | Логаут удаляет запись — cookie больше не работает; просроченная сессия не проходит; смена роли подхватывается без пересоздания сессии | unit |
| Лента/поиск | Пагинация; приватные и processing/failed/hidden не попадают в ленту; поиск находит по подстроке названия | unit |

## 3. Пирамида

- **Unit (без Docker):** сервисы (видимость видео, права, дедупликация просмотров, счётчики реакций), валидаторы загрузки (magic bytes по фикстурам-байтам), хелперы. Моки: репозитории, storage-интерфейс, очередь (заглушка `enqueue`).
- **Integration (маркер `integration`):** эндпоинты через httpx ASGI-транспорт + реальная БД PostgreSQL (testcontainers не используем — БД поднимаете вы), S3 через `minio-py` (клиент совместим с Silo), транскод-воркер на реальном ffmpeg с крошечным тестовым роликом (тестовая фиксттура генерируется ffmpeg testsrc, <1 МБ).
- **E2E (ручные):** полный сценарий в браузере; деплой на чистой Ubuntu.

## 4. Инструменты

- `pytest` + `pytest-asyncio`, `httpx` (ASGI-транспорт), `factory-boy` не нужен — фиксттуры вручную.
- Линтер: `ruff` (uv run ruff check .).
- Покрытие не гоняемся — цель: обязательные области из таблицы выше.

## 5. Что требует вашего ручного запуска

1. `docker compose --profile integration up -d` (или отдельный compose для тестов — уточню при реализации): тестовая БД + Silo + Redis → затем `uv run pytest -m integration`.
2. Полный сценарий в браузере: регистрация → загрузка → просмотр → лайк → комментарий (чек-лист в plan.md, этап 1).
3. `bash deploy.sh` на чистой Ubuntu VM → проверка, что всё поднялось одной командой.
