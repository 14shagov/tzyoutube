# ADR-002: Фоновая очередь — arq + Redis

Статус: принято.

## Контекст

Транскодирование ffmpeg занимает десятки секунд и не должно блокировать HTTP-запрос загрузки; нужны повторы при сбоях и статусная модель (processing → ready | failed). Всё приложение на asyncio (FastAPI).

## Варианты

1. **Celery + Redis/RabbitMQ.** Зрелый, но тяжёлый: отдельный брокер или конфиг, синхронная модель, больше зависимостей.
2. **RQ + Redis.** Проще Celery, но слабее ретраи/типизация, синхронный.
3. **arq + Redis.** Async-native (одна модель с FastAPI), лёгкий, ретраи из коробки, воркер запускается как отдельный процесс того же образа.

## Решение

`arq` на Redis 7. Воркер `src/worker/` выполняет задачи `transcode(video_id)` и `cleanup_video(video_id)`; `retries=2`, после исчерпания — `videos.status='failed'` (для cleanup — запись сохраняется, задача ретраится). Redis используется только очередью и rate limit.

## Зачем нужен Redis (и что было бы без него)

Redis несёт две функции: (1) очередь задач с ретраями и отложенными повторами; (2) быстрые счётчики rate limit (5 неудачных входов/10 мин/IP, 3 регистрации/час/IP).

Альтернатива без Redis — очередь на PostgreSQL (`SELECT ... FOR UPDATE SKIP LOCKED`): работает, но требует самописного воркер-цикла, ретраев и блокировок — это собственная имплементация того, что arq даёт из коробки. Rate limit без Redis лёг на атомарность в PG (INSERT/UPDATE на каждый вход) либо на in-memory счётчики, которые теряются при рестарте и не делятся между процессами.

## Последствия

- Плюс: минимум зависимостей, единый event loop, простая отправка задачи из API (`arq.create_pool`), проверенные ретраи и rate limit.
- Минус: +1 сервис в стеке (лёгкий, без персистентности — потеря очереди при падении допустима: задачи восстанавливает перезапуск транскода или ручной retry, статусная модель в PG не теряется); сообщество меньше, дашборда нет — для тестового задания не нужно.
