# ADR-001: Объектное хранилище — Silo (форк MinIO)

Статус: принято; пересмотрено 2026-11-11 (образ `minio/minio` удалён с Docker Hub — репозиторий MinIO заархивирован).

## Контекст

По ТЗ нужна загрузка видео до 512 МБ, транскодирование, превью и раздача с поддержкой Range-запросов. Хранить большие бинарники в PostgreSQL нельзя; система должна разворачиваться одной командой на чистой Ubuntu без внешних облачных аккаунтов.

Изначально выбран MinIO. В ходе ручной проверки стека выяснилось: проект MinIO заархивирован, официальный образ `minio/minio` удалён с Docker Hub — воспроизводимый деплой по этому образу невозможен. Нужна замена с тем же S3 API.

## Варианты

1. **Файловая система (том контейнера).** Просто, но нет presigned URL и bucket-политик: пришлось бы самому писать раздачу с Range и проверку прав в NGINX/приложении; сложнее бэкап.
2. **pgsty/silo (форк MinIO, S3-совместимый).** Presigned URL, политики бакетов, Range из коробки; API и переменные окружения (`MINIO_ROOT_USER`/`MINIO_ROOT_PASSWORD`) совместимы с MinIO; образ доступен на Docker Hub с версионированными тегами.
3. **RustFS.** S3-совместимый на Rust, но проект молодой, экосистема и совместимость с minio-py/mc менее проверены.
4. **SeaweedFS.** Зрелый, но S3-слой — надстройка над собственной моделью (filer/volume); совместимость SigV4/presigned имеет больше оговорок.
5. **Garage.** Лёгкий S3-совместимый, но меньшая команда, меньше документации по edge-кейсам presigned за reverse proxy.
6. **Внешний S3 (AWS).** Нарушает требование самодостаточности (чистая Ubuntu, одна команда), требует аккаунт и платёжные данные.

## Решение

**pgsty/silo** в том же Docker Compose-стеке, образ зафиксирован тегом `pgsty/silo:RELEASE.2026-09-16T00-00-00Z` (плавающие теги и `latest` запрещены). Приложение обращается к хранилищу только через стандартный S3 API (endpoint и ключи из окружения: `S3_ENDPOINT`, `S3_ACCESS_KEY`, `S3_SECRET_KEY`) — замена хранилища на любой S3-совместимый сервис не требует правок кода. Клиентская утилита (если понадобится для инициализации бакетов) — только `pgsty/mc` с зафиксированным тегом.

Бакеты: `raw` (приватный, исходники), `videos` (приватный, транскоды), `thumbnails` (public-read). Порты хранилища наружу не публикуются — доступ через NGINX `/videos/`, `/thumbnails/`, `/media/thumbnails/` или из внутренней сети compose.

## Последствия

- Плюс: presigned URL, политики бакетов, Range/206 из коробки; код не отличается от MinIO (совместимый API), локальная разработка идентична S3.
- Плюс: версионированный тег образа — воспроизводимый деплой.
- Риск: Silo — сторонний форк; лицензия AGPLv3 (унаследована от MinIO). Для тестового задания использование образа по AGPL допустимо (мы не модифицируем и не распространяем его код), но при коммерческом встраивании нужна отдельная оценка.
- Риск: совместимость с minio-py/mc — best-effort со стороны мейнтейнера форка; зафиксированный тег образа снижает риск тихих регрессий. Проверено вручную: healthcheck жив, бакет `videos` создаётся, `/videos/*` отдаёт AccessDenied без подписи (ожидаемое поведение).
- Минус: ещё один сервис в стеке (память ~сотни МБ) — приемлемо для тестового задания.
- Минус: это не CDN — для ТЗ достаточно.
