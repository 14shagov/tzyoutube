# Безопасность

## 1. Модель угроз

| № | Угроза | Вектор | Вероятность / влияние |
|---|---|---|---|
| T1 | Подбор пароля / credential stuffing | Массовые попытки входа и регистрации | Высокая / критично (угон аккаунта) |
| T2 | XSS | Вставка HTML/JS в комментарии, названия, описания каналов и видео | Средняя / критично (кража сессии, дефейс) |
| T3 | IDOR | Прямые запросы к чужим приватным видео через /api/videos/{id} и /media | Средняя / критично (утечка приватного контента) |
| T4 | Утечка по прямой ссылке на хранилище | Раздача медиа-объектов без проверки прав | Средняя / критично |
| T5 | Вредоносные загрузки | Файл-полиглот, вредоносный «видео»-контейнер | Средняя / высокое |
| T6 | Секреты в репозитории | .env, ключи в коммитах и логах | Средняя / критично |
| T7 | Повышение привилегий | Использование роли из устаревшей сессии без сверки с БД | Средняя / критично |
| T8 | Спам жалобами/комментариями | Массовая подача жалоб и комментариев | Низкая / среднее |
| T9 | Исчерпание ресурсов | Сверхкрупный файл, флуд запросами | Средняя / среднее |

## 2. Меры

### 2.1 Пароли и вход (T1)

- Хэширование bcrypt, cost 12 (страж `test_production_bcrypt_cost.py` фиксирует cost в коде; в юнит-тестах cost 4 через monkeypatch).
- Сессии: HttpOnly + SameSite=Lax cookie `session_id`, TTL 14 дней; серверные записи в таблице `sessions`.
- Rate limit (в приложении, ключ — X-Real-IP, который nginx перезаписывает на $remote_addr):
  5 неудачных попыток входа с одного IP за 10 минут → 429 (считаются ТОЛЬКО неудачные;
  лимит сначала проверяется peek-ом, до любого хеширования); 5 регистраций / 10 мин с IP —
  счётчик бьёт до bcrypt. Помимо этого nginx ограничивает `location /auth/` (limit_req).
- Для чужого email выполняется dummy-проверка bcrypt той же стоимости — нет enumeration по таймингу.
- Ошибка входа — единый generic-ответ, не раскрывающий существование email.
- Логаут удаляет запись сессии в БД и идемпотентен: невалидный UUID cookie → 204 (без 500);
  401 только при отсутствии cookie. При успешном входе протухшие сессии вычищаются
  (`purge_expired_sessions`, B7).

### 2.2 Сессии и токены (T7)

- Cookie `session_id` — UUID записи БД, не подпись и не JWT: отзыв мгновенный удалением записи.
- Роль и флаг блокировки проверяются из БД на каждом запросе; сессия роль не кэширует.
- Все cookie-флаги: `HttpOnly`, `SameSite=Lax`; `Secure` — отдельная настройка `COOKIE_SECURE` (по умолчанию выключена): флаг решает деплоймент (есть HTTPS или нет), а не APP_ENV — production-деплой по plain HTTP обязан работать (ревью m01882).

### 2.3 Валидация загрузок (T5, T9)

- Белый список расширений: mp4, webm, mkv, mov, avi.
- Проверка magic bytes / сигнатуры контейнера, а не только расширения.
- Лимит размера `MAX_UPLOAD_SIZE` (512 МБ): nginx принимает 512m ТОЛЬКО на
  `location = /api/videos` (общий лимит 10m) с `proxy_request_buffering off`;
  приложение сначала проверяет Content-Length (413 до чтения тела / 400 на
  «мусорном» заголовке), затем enforced по мере чтения стрима (413).
- Загруженный файл не исполняется: отдаётся только как объект S3-хранилища; ffmpeg работает с копией в tmp-каталоге воркера.
- Имена объектов — UUID, сгенерированные сервером; пользовательское имя файла не используется.
- ffmpeg в воркере захарден: `-nostdin`, `-protocol_whitelist file` (никаких
  внешних протоколов на пользовательских файлах), `-threads 4`, апскейл
  запрещён (`scale=-2:'min(480,ih)'`), превью — явный `-map 0:v:0`. Результат
  валидируется ffprobe (контейнер/кодеки/duration) до аплоада; падение/таймаут
  → статус `failed` с `failure_reason`; hung ffmpeg убивается процессом
  (create_subprocess_exec + kill), arq `job_timeout` 660s > ffmpeg 600s,
  `max_jobs=2`.

### 2.3a Валидация входных данных (B-группа ревью)

- Пагинация: `limit` 0..100, `offset` ≥ 0 на всех списках → иначе 422.
- `title` ≤ 200 символов (`Form(max_length=200)` → 422, не 500 от БД).
- Гостевой cookie `guest_id` ≤ 64 символов и charset `[A-Za-z0-9_-]` —
  иначе перевыдаётся свежий токен.
- Поиск ILIKE экранирует спецсимволы LIKE: обратный слеш, `%`, `_` (`escape_ilike` + `ESCAPE '\'`).
- Индекс поиска: pg_trgm + GIN (gin_trgm_ops) по `videos.title`.

### 2.4 XSS (T2)

- Jinja2 автоэкранирование по умолчанию; нигде не отключать (`| safe` под запретом без явной причины).
- Пользовательский контент (комментарии, названия, описания) экранируется на выводе.
- REST API возвращает JSON; экранирование не требуется, но строки нормализуются и обрезаются по длине.
- Content Security Policy базового уровня: `default-src 'self'` (медиа с домена хранилища — `img-src`/`media-src` явно).

### 2.5 IDOR и приватность (T3)

- Проверка доступа в сервисном слое для каждого эндпоинта, работающего с video_id / channel_id.
- Приватное/скрытое видео для неавторизованных и без права доступа → 404 (не раскрываем существование).
- Белый список `video_acl` проверяется в том же сервисном методе `check_video_access`.
- Тесты на IDOR обязательны (см. testing.md).

### 2.6 Раздача медиа (T4)

- Presigned GET URL: TTL 3600 с для публичных видео (`PRESIGNED_TTL_SECONDS`) и только 900 с для приватных (`PRESIGNED_TTL_PRIVATE_SECONDS`) — утёкшая ссылка не должна жить часами; выдача только после `check_video_access`.
- В presigned URL на воспроизведение принудительно задаются `response-content-type=video/mp4` и `response-content-disposition=inline`, чтобы браузер проигрывал видео, а не скачивал (актуально и для объектов, загруженных до появления явного content_type при записи).
- Бакет `raw` закрыт полностью; публичная политика только на `thumbnails`.
- NGINX проксирует `/media/` → хранилище; прямые порты хранилища наружу не публикуются.

### 2.7 Секреты (T6)

- Все секреты — переменные окружения (`.env`, генерируется `deploy.sh` при первом запуске).
- В репозитории только `.env.example` с плейсхолдерами; `.env` в `.gitignore` с первого коммита.
- Перед каждым коммитом — просмотр `git diff --cached`.
- Секреты не логируются; логирование настроено на уровни событий, а не на дампы запросов.

### 2.8 CORS

- Фронт и API — один origin (NGINX), поэтому CORS закрыт: запрещаем wildcard, разрешён только собственный origin при необходимости.

### 2.9 Права на хранилище

- Ключи приложения в хранилище — минимальные: read/write в нужных бакетах, отдельная пара для воркера не требуется (один сервисный аккаунт на приложение).
- Root-ключи хранилища используются только при первичной инициализации бакетов.

### 2.10 Reverse proxy и контейнер (C-группа ревью)

- Security-заголовки на все ответы: `X-Content-Type-Options: nosniff`,
  `X-Frame-Options: DENY`, `Referrer-Policy: no-referrer-when-downgrade`.
- `X-Real-IP` nginx всегда перезаписывает на `$remote_addr` (additive-заголовки
  клиент-подделываемы); приложение доверяет только X-Real-IP.
- `limit_req` на `/auth/` (зона по `$binary_remote_addr`).
- Контейнер приложения не запускается от root: системный пользователь `app`,
  `USER app` после сборки; единственный опубликованный порт — nginx.

### 2.11 Матрица прав API (этап 3–4, группы 3A–3E)

Роль и блокировка читаются из БД на каждом запросе (сессия не кэширует) —
смена роли/блокировка админом действует сразу, без пересоздания сессии (T7).

| Группа эндпоинтов | guest | user | владелец | moderator | admin |
|---|---|---|---|---|---|
| GET /api/channels/{id}, /videos, /playlists | 200 (публичное) | 200 | 200 (видит приватное) | 200 | 200 |
| PATCH /api/channels/{id} | 401 | 403 | 200 | 403 | 403 |
| POST/DELETE /api/channels/{id}/subscribe | 401 | 204 (self → 422) | 204/422 | 204 | 204 |
| GET /api/subscriptions, /api/feed/subscriptions | 401 | 200 | 200 | 200 | 200 |
| PATCH/DELETE /api/videos/{id}, ACL CRUD | 401 | 403 | 200/204 | DELETE 204, PATCH 403 | DELETE 204, PATCH 403 |
| GET /api/me/videos, GET /api/videos/{id}/status | 401 | 200 (своё) | 200 | 200 (любое не-deleted) | 200 |
| Плейлисты CRUD + items | 401 | 403 чужие | 200/201/204 | 403 чужие | 403 чужие |
| GET /api/playlists/{id} приватного | 404 | 404 | 200 | 404 | 404 |
| POST /api/videos/{id}/report | 401 | 201 (повтор → 409) | 201 | 201 | 201 |
| GET /api/mod/reports, POST /api/mod/reports/{id}/resolve | 401 | 403 | 403 | 200/201 | 200/201 |
| PATCH /api/admin/users/{user_id} | 401 | 403 | 403 | 403 | 200 (self → 422) |

- Скрытое (hidden) видео: нет в ленте/поиске/канале (фильтр `status='ready'`),
  карточка и play_url — только владельцу и staff; остальным 404.
- Приватное видео: владелец + staff + записи `video_acl`; остальным 404.
- Все права покрыты тестами матрицей ролей: `tests/test_moderation_api.py`,
  `tests/test_video_manage_api.py`, `tests/test_playlists_api.py`,
  `tests/test_channels_api.py`, `tests/test_subscriptions_api.py`,
  `tests/test_access_unit.py`, `tests/test_video_status_api.py`.

## 3. Что осознанно не делаем (и почему)

| Мера | Почему отложена |
|---|---|
| 2FA | Не проверяется сценарием, не успеваем по сроку |
| TLS-сертификаты | Тестовая VM, HTTP за NGINX; LetsEncrypt требует домен — оставлено как опция deploy.sh |
| WAF | Избыточно для тестового задания |
| Автоматический антивирусный скан загрузок | Требует ClamAV в стеке; фиксируем как будущее улучшение |
